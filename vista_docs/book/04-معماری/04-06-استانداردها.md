# استانداردها

قاعده روشن است: استاندارد موجود را می‌پذیریم و فقط شکاف‌های واقعی را با افزونهٔ نسخه‌دار پر می‌کنیم. هدف این است که سرویسِ دارای MCP بتواند همان پیاده‌سازی را بیاورد و برای استفادهٔ پایه مجبور به ساخت قرارداد ویستا نشود.

## لایه‌ها

| موضوع | مبنا |
|---|---|
| اعلام و فراخوانی قابلیت | MCP |
| رابط تعاملی اختیاری | MCP Apps، یا مینی‌اپ پشتیبانی‌شده |
| اتصال حساب و ورود مشترک | OAuth و OIDC در مسیرهای مربوط |
| فرادادهٔ انتشار | قالب‌های MCP Registry، با افزونهٔ محدود ویستا |
| اختیار خرید و پرداخت | AP2 و افزونه‌های لازم برای دامنهٔ ویستا |
| رابط اجرا و طرح‌واره‌ها | OpenAPI و JSON Schema |
| مدل | رابط قابل تعویضِ ارائه‌دهندگان |
| تجربهٔ کاربر | واژگان آشنای گفت‌وگو، بات، پیوست و استارت |

## یک MCP، دو سطح یکپارچه‌سازی

**سطح پایه، MCP معمولی است.** احراز استاندارد، ابزارهای پشتیبانی‌شده و نمایش نتیجه کافی‌اند. قرارداد، کلید امضای ویستا، بات و مینی‌اپ الزام ورود به این سطح نیستند. قرارداد اتصال را ویستا برای تعهد خودش فراهم می‌کند و آن را به امضای ارائه‌دهندهٔ بیرونی نسبت نمی‌دهد.

**سطح قرارداد، افزودهٔ اختیاری است.** اپ ابزارهای ساخت و تکمیل پیش‌نویس را با همان MCP می‌دهد و رابط جداگانهٔ اجرای قرارداد و رویدادهای پس از آن را پیاده می‌کند. مشتری معمولی MCP می‌تواند ابزارها را صدا بزند، اما فهم و اجرای قرارداد ویستا به پشتیبانی این پروفایل نیاز دارد.

خواندن، ساخت پیش‌نویس و نوشتن سبکِ مجاز از مسیر قابلیت‌اند. اجرای قرارداد از مسیر پردازشگر با اعتبارنامهٔ جداست؛ پنهان کردن یک ابزار اجرایی MCP همان جداسازی نیست. اتصال بیرونی هم نباید فقط به این دلیل که به کیف پول ویستا راه ندارد، اختیار مالی نامحدود روی حساب خودش بگیرد.

MCP Apps اختیاری است. پشتیبانی از ابزار به‌تنهایی تضمین نمی‌کند که رابط گرافیکی کامل و مناسبی ساخته شده؛ مسیر مستقیم هر قابلیتِ عرضه‌شده باید آزموده شود.

## هویت و اتصال حساب

OAuth مجوز دسترسی به منبع است؛ OIDC برای هویت ورود به کار می‌آید. ورود با شماره و رمز یک‌بارمصرف می‌تواند روش احراز در ویستا باشد و با این استانداردها تعارضی ندارد.

شریک همکار می‌تواند هویت ویستا را بپذیرد. سرویس بیرونی از روش مجوز خودش استفاده می‌کند. گواهی «به نیابت از» فقط به شریکِ پشتیبان این قرارداد داده می‌شود؛ MCP معمولی مجبور به شناخت آن نیست. اعتبارنامه متناسب با حساب و مقصد انتخاب می‌شود و به مدل نمی‌رسد.

## انتشار بدون جستجوی بیرونی

برای معرفی سرویس، از قالب فرادادهٔ استاندارد و افزونهٔ نسخه‌دار ویستا استفاده می‌کنیم. اطلاعات نصب کاربر، توکن‌ها و تصمیم احراز مالی جزو فرادادهٔ عمومی ناشر نیستند. [مستندات MCP Registry](https://modelcontextprotocol.io/registry/about).

این انتخاب، تعهد به جستجو یا گردآوری رجیستری‌های بیرونی نیست. در سه فاز نخست، جستجو فقط میان اتصال‌های کاربر و فهرست ویترین است.

## قرارداد بر پایهٔ AP2

مبنای اختیار خرید و پرداخت، AP2 است. این استاندارد اختیار خرید را به شرایط امضاشدهٔ فروشنده و اختیار پرداخت را به همان خرید پیوند می‌دهد و برای نتیجه رسید دارد. از نقاط گسترش آن برای ابزار پرداخت و محدودیت‌های دامنه استفاده می‌کنیم؛ AP2 جای دفتر مالی یا توافق تسویه را نمی‌گیرد. [مشخصات AP2](https://ap2-protocol.org/ap2/specification/).

برای شرکایی که به ویستا اعتماد می‌کنند، الگوی **Trusted Agent Provider** مبنای مناسبی است: سطح قطعی نمایش قرارداد رضایت می‌گیرد و کلید حفاظت‌شدهٔ سکو آن را گواهی می‌کند. مدل به کلید یا استفادهٔ خارج از این سطح دسترسی ندارد. این گواهی را نباید امضای کلید شخصی کاربر نامید. [چارچوب اختیار AP2](https://ap2-protocol.org/ap2/agent_authorization/).

مجوزهای غیرمالی، شرایط سرمایه‌گذاری، فروش دارایی، پله‌های احراز محلی و قواعد وکالت باید نگاشت صریح داشته باشند. چیزی را صرفاً با نام «پرداخت» سازگار نمی‌کنیم. جزئیات و آزمون انطباق در SDK می‌آید؛ نسخهٔ استاندارد و نوع اسناد باید آنجا تثبیت شوند.

قاعدهٔ عمومی «اپ همیشه اول امضا می‌کند» نداریم. نوع قرارداد تعیین می‌کند چه طرف‌ها و چه اثبات‌هایی لازم‌اند؛ الزامات فروشنده در خرید AP2 همچنان برقرارند.

## جمع‌بندی

MCP پایهٔ مشترک است و قرارداد ویستا افزودهٔ آن. AP2 مبنای اختیار مالی است، با گسترشِ شکاف‌ها. اتصال حساب، انتشار و رابط تصویری هم از استانداردهای مربوط استفاده می‌کنند. پروفایل‌ها جدا هستند تا پیوستن ساده بماند و سازگاری پروتکلی با تعهد مالی اشتباه نشود.
